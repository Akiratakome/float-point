# Week 7 Report 1 Harness Pipeline Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a reproducible Week 7 Report 1 evidence pipeline for the Euler validation, compiler-flag, implementation-variation, and 1600² GPU reference-candidate experiments without changing solver numerics or cfg defaults.

**GPU strategy:**

- Week 6 produced bit-identical CPU↔GPU strict-IEEE smoke evidence for Sod and LW3 (`experiments/week6/regression/summary.md`, `experiments/week6/csc_smoke/summary.md`). Those rows used the Week 6 smoke cfgs and are canonical GPU bring-up evidence, not proof that every later solver/resolution pair is bit-identical.
- The 1600² LW3 reference base point (Task 11) is a **GPU double strict-IEEE high-resolution reference candidate** on CSC. Task 9's HLLC strict CPU↔GPU preflight is a hard scientific gate before Task 11 runs, not a decorative evidence row. A single RTX 5090 should be fast enough for 1600², but the 8–15 min estimate is an extrapolation from `experiments/week6/csc_smoke/runs/lw3-gpu-csc-d` and must be recorded as provisional until measured.
- Tasks 6–8 add LW3 200²/400² CPU and GPU evidence so the Week 7 evidence covers the 1D + 2D + CPU + GPU + float + double validation cells without re-running the whole Week 6 matrix. 1D cases stay CPU-only because their grid sizes are far below GPU occupancy thresholds.
- This plan is the Report 1 evidence-critical subset of the nominal Week 7 matrix in `docs/requirement/overall.md`. It does **not** claim to complete the full 7-case × precision × device × compiler-flag Cartesian sweep or a convergence sweep; those remain optional follow-up work after the Report 1 pipeline is reproducible.

**Architecture:** Keep the canonical harness flow `config -> build -> run -> measure -> aggregate -> plot`. Use existing build, run, regression, metrics, aggregation, and plotting entry points; add one new report script (`scripts/regression/matrix_summary_report.py`, Task 3) that consumes `matrix_summary.json` so each Week 7 matrix produces real scalar summaries. Treat 1600² as a separate GPU reference-base job family, not a full Cartesian sweep.

**Tech Stack:** CMake/Ninja, C++17/CUDA binaries produced by existing CMake flags, Python harness scripts under `scripts/`, Bash build/regression scripts, JSON matrix files, Markdown/CSV/JSON summaries, Matplotlib figures, SLURM submission helpers under `scripts/cluster/`.

**Naming clarification — the word "strict" appears twice with different meaning:**

- `cpu-double-O2-ieee-strict` etc. (from `scripts/build_matrix.py`): `strict = RIEMANN_STRICT_INEQUALITY=ON` → HLLC `<` instead of `<=`.
- `build-cuda-double-strict` / `build-cpu-strict-double` (from `scripts/build_all.sh`): `strict = STRICT_IEEE=ON` → `-ffp-contract=off`, `-fno-fast-math`, etc. RIEMANN_STRICT_INEQUALITY is **off** (i.e. `<=`) in these builds.

Confusing the two will produce wrong evidence. Each task below names the build directory explicitly; do not paraphrase.

- [ ] **Step 1: Define the script CLI and contract**

`scripts/regression/matrix_summary_report.py` accepts:

```text
matrix_summary_report.py <matrix_summary.json> [--gamma 1.4] [--pair-by precision|build|none] [--pair <left-run-name> <right-run-name> --pair-label <label>] [--reference exact|<path>] [--out <prefix>] [--with-phase] [--filter-name-contains <comma-separated-substrings>]
```

It reads `matrix_summary.json`, then for each run:
1. Reads the run's `metadata.json` (for `name`, `precision`, `build`, `source_config`, `timing`).
2. Reads the run's binary grid via `scripts/io_helper.py:read_binary` if `raw_output` is set.

It then computes:
- Per-run scalars: `nx`, `ny`, `t_end`, `total_s`, integral max/min of conserved variables, L1/L∞ of (run − pair), `ulp_max` where same-precision pair exists.
- Pair definitions:
  - `--pair-by precision` (default): match runs by stripping `precision` from their name (e.g. `sod-cpu-double-o2-ieee-leq` ↔ `sod-cpu-float-o2-ieee-leq`); compares always cast both to f64 before subtracting.
  - `--pair-by build`: match by stripping the `build` slug; useful for HLLC-vs-Rusanov style sensitivity.
  - `--pair-by none`: no pairing, only per-run scalars.
  - Repeated explicit pairs: `--pair <left-run-name> <right-run-name> --pair-label <label>`; this is required for axis-isolation reports in Task 8 because implicit name stripping is too brittle for compiler/implementation variation rows.
- Optional filters:
  - `--filter-name-contains "a,b"` keeps runs whose names contain any listed substring. Use this only for small explicit axis reports.
  - `--with-phase` adds 2D phase metrics when both paired binaries are 2D with identical shape.
- Outputs `summary.csv`, `summary.json`, `summary.md` next to the matrix summary unless `--out <prefix>` is given.

Stationary-contact-style zero-denominator metrics (`philip_ratio` etc.) are reported as `n/a` rather than `inf`.

- [ ] **Step 2: Implement the script**

The implementation re-uses helpers:
- `read_binary` from `scripts/io_helper.py`.
- The degenerate-case policy from this plan, not the exact `_safe_ratio` implementation in `scripts/regression/float_regression_report.py`: `0/0` can be reported as `1.0` when a ratio is meaningful, but nonzero divided by zero must be reported as `n/a`/`None` in Week 7 summaries rather than propagating `inf`.
- For 2D cases, optionally call `compute_phase_metrics_from_primitive` (`scripts/metrics/phase_error_metrics.py`) when both runs in a pair share `ny > 1` and the user passes `--with-phase`.

The script must NOT compare different-precision runs by ULP gate; the `ulp_max` field is only meaningful when the precision tag of both binaries matches. Mixed-precision pairs report L1/Linf only and leave `ulp_max = n/a`.
