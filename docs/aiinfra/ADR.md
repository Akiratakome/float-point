# 架构决策记录（ADR）

> *Architecture decision records for workload family 2. Written in Chinese because it doubles
> as interview-preparation material.*
>
> 每条的结构固定为 **决策 / 备选 / 为什么否掉备选 / 这个决策的代价**。
> 面试被追问时按这个结构回答 —— 能说出"我考虑过什么、为什么没选、付出了什么"，
> 比说出结论本身更有说服力。
>
> 执行计划见 [`PLAN.md`](PLAN.md)。

---

## ADR-1：把"数值确定性"而不是"吞吐"做成 headline

**备选**：标准的 TTFT/TPOT/吞吐 benchmark。

**为什么否掉**：这是所有人都在做的，无法差异化，且我在吞吐绝对值上永远赢不过有 H100 集群的
候选人。确定性这条线我有独有资产（HRSC 上已证明 nvcc FMA 合并破坏位级一致），而且它有同行评审级
的学术锚点（arXiv:2506.09501、RepDL arXiv:2510.09180、Verificarlo CI arXiv:2407.08262）与工程
锚点（Thinking Machines batch-invariance；LMSYS SGLang 确定性推理自述 50 次采样 1 个唯一输出、
开销 24.4%–55.1%）。

**代价**：36 份 JD 里直接写 `numerics` 的只有 1 份，宽度必须靠性能矩阵补。

## ADR-2：7B 作为跨架构匹配比较点

**显存边界推导**：7B fp16 权重约 14 GB，A30 24 GB 单卡装得下并留 KV cache 余量；5090 32 GB 更宽松。
更大的模型只能在 5090 侧跑，就不再是匹配比较。

**备选**：0.5B（跑得快但 kernel 太小、掩盖带宽效应）；14B+（A30 单卡装不下，被迫 TP=2，混入互联因子）。

**代价**：7B 的绝对规模不亮眼，必须用"覆盖多少种配置"而不是"跑多大模型"来讲规模。

> **2026-08-24 修订**：本地只有 8 GB 显存，7B 无法在本地验证。本条仅适用于集群侧；本地侧见 ADR-12。

---

## ADR-3：主后端选 vLLM，PyTorch eager 作参考基线

eager 是 fidelity 的黄金参考（语义最简单、最可预测）；vLLM 是 JD 出现频次最高的引擎，且它的连续
批处理与 PagedAttention 正是**真正会破坏确定性的机制** —— 它既是覆盖面需求也是实验对象。

**备选**：TensorRT-LLM 作主后端。**否掉原因**：构建链更重，在消费级 `sm_120` 上的支持面需要额外
验证，会把预算吃掉。SGLang 作为可选第二引擎（它自己发布过确定性推理工作，是天然对照）。

**代价**：TRT-LLM 在 NVIDIA 系 JD 中出现，本方案不覆盖。

---

## ADR-4：保留 HRSC 作为第二负载族

这不是"舍不得旧项目"。它有两个不可替代的作用：

1. 证明 harness 不是为 Transformer 硬编码的 —— 这正是 `run_matrix.py` 加性泛化要证明的事；
2. 提供"同一套数值 qualification 方法在两个完全不同负载上成立"的对照，把结论从"LLM 的一个现象"
   提升为"浮点系统的一般性质"。

**代价**：叙事要多讲一层，需要在根 README 里用一段话说清两者关系。

---

## ADR-5：算子选题是 batch-invariant 归约，不是复刻 FlashAttention

**备选**：复刻 FlashAttention。**否掉原因**：那是纯性能题，我大概率做不过官方实现，做出来也只是
"又一个教程级 kernel"。batch-invariant 归约直接服务于 headline —— 它是"恢复确定性要付出多少代价"
这个问题的实现手段，同时照样覆盖 Triton + CUDA + 算子融合 + Nsight 这些关键词。

**代价**：微基准上它可能比现有 kernel 慢。但**这是预期结果而不是失败**，因为成本正是要测量的量。

## ADR-6：精度轴 = {fp32+TF32关, fp32+TF32开, fp16, bf16, fp8(仅 5090), W8A8 或 AWQ 择一}

TF32 开/关拆成两档，因为 TF32 是 PyTorch 默认行为里最容易被忽略的精度变化，且它正是"请求的精度
≠ 有效的精度"的典型案例。FP8 只在 5090 可用 —— **这不是缺陷而是设计**：它触发 harness 里已存在的
`unsupported_capability` 分类，产出结构化的能力矩阵而不是空白格。

**代价**：量化方法只做一种，不做 SmoothQuant/AWQ/GPTQ 横评。

---

## ADR-7：TP 只到 2，明确标注 intra-node；多节点证据从 CPU 侧取

2 GPU 是官方 per-job 硬上限，不是选择；集群唯一 4 卡机器 `hex` 是 Kepler `sm_35`，CUDA 12.0 已
移除其支持，实际不可用。

**备选**：放弃分布式这条线。**否掉原因**：集合通信在 JD 中约出现 6 次，是仅次于 PyTorch 的缺口。
2 卡仍能产出真实证据，**而且 A30（可能有 NVLink）与 5090（消费级无 NVLink，走 PCIe）的互联差异
会让同样的 TP=2 产生完全不同的扩展效率** —— 2 卡规模下这反而是最有价值的对照，因为它证明扩展效率
由互联决定而非卡数。多节点这一课改从 CPU 侧补（步骤 9）。

**代价**：绝不能说成"分布式训练经验"，必须写 "intra-node tensor-parallel topology case study"；
扩展性曲线无法提供。

## ADR-8：headline 指标用"重复 N 次的唯一输出个数"，而不是 logits 的 L2 差

唯一输出数是二值可判、非专家也能理解、且可证伪的；logits 差是连续量，需要先回答"多大算大"。
正确的关系是：**唯一输出数做 headline，logits ULP/L2/KL 做机制解释**。这与 LMSYS 的报告格式一致。

**代价**：唯一输出数对短输出不敏感，必须设定足够的输出长度 —— 这一条直接约束了步骤 0 的 spike 配置。

---

## ADR-9：先测同硬件同配置的重复噪声地板，再看跨架构差异

没有地板就无法区分"舍入噪声"与"真实退化"。这是我在 HRSC 上用 Verificarlo MCA 建立的核心方法论，
直接迁移。**任何跨架构差异必须先证明它超出同配置重复的噪声范围才能被称为差异。**

**代价**：每个配置多一轮重复采样的预算。

---

## ADR-10：每个计时结果必须携带共租户证据

`csc-mphil-gpu` 节点非独占（最多 4 个作业同节点）。不记录共租户就无法判断延迟数字是否被污染。
**剔除策略必须预先声明**（例如：作业期间检测到其他 GPU 进程即标记为 non-headline），
而不是事后挑数据。

**代价**：部分运行会被作废需要重跑，排期要留冗余。

## ADR-11：不租用云 GPU，分布式证据止于学校可得的 2 卡 + CPU 多节点

*决定于 2026-08-24。*

**备选**：租云卡做 8–16 卡的最小分布式训练。已完成成本核算（官方价格，2026-08-24）：

| 方案 | 单价 | 4h 会话 |
|---|---|---|
| RunPod 单节点 8×A100 SXM | $1.59/GPU/hr → $12.72/hr | ≈ $51 |
| RunPod Instant Clusters 2 节点 16×A100（节点间 1600 Gbps） | $25.44/hr | ≈ $102 |
| Lambda 按需 8×A100 SXM / 8×H100 SXM / 8×V100 | $2.79 / $3.99 / $0.79 per GPU/hr | — |
| ~~Lambda 1-Click Clusters~~ | H100 $5.54–6.16/GPU/hr，**最小 16 卡 + 最短 2 周承诺** | **≈ $29,800** |
| SF Compute | H100 from $1.73/GPU/hr（最便宜） | VM 上的 InfiniBand 要到 Q3 2026，自助拿不到多节点 IB |

**为什么否掉**：项目主张是**数值确定性**，而确定性证据不依赖卡数 —— 2 卡即可测出并行度改变归约
顺序的效应，8 卡只是把同一效应放大。花钱买的是规模数字，而规模数字恰恰是本项目**不**主打的维度。

**代价**：拿不到 8–16 卡的并行策略对照与扩展性曲线，必须在对外材料中诚实标注。

**这条本身是可讲的面试内容**：说明我做过成本收益核算并据此拒绝了一笔支出，而不是没想到。

## ADR-12：模型分两层 —— 本地 0.5B 走全流程，7B 只上集群

*决定于 2026-08-24，设计评审中发现。*

**触发事实**：本地 GPU 只有 **8,151 MiB**。7B fp16 权重约 14 GB，**本地根本装不下**。
原计划"所有脚本先在本地跑通再上集群"这条成本控制前提，对 7B 路径是破的。

**备选**：

- **把匹配比较点降到 1.5B**，全流程本地可跑。**否掉原因**：模型越小，decode 越容易被 kernel launch
  开销而不是显存带宽支配，1.92× 的带宽预测（实验 E1）就失去了检验价值。
- **放弃本地开发**，全部在集群迭代。**否掉原因**：集群节点非独占、6h 上限，第一次跑就撞未排练的
  bug 很贵。

**决策**：本地用 `Qwen2.5-0.5B-Instruct` 走通全部代码路径（确定性、保真度、聚合、图表），
集群用同家族的 `Qwen2.5-7B-Instruct` 跑同一套已验证的代码。同家族才能让两层结论互相说明。

**代价**："模型规模"成为一个未被本地覆盖的维度，7B 首次运行仍可能暴露 OOM 与 KV cache 配置问题 ——
但那类问题本来就只能在真显存上暴露。

## ADR-13：一个容器 digest 打通三张卡，否则把软件栈记为显式实验轴

*决定于 2026-08-24，设计评审中发现。这是评审最有价值的产出。*

**触发事实**：本地 5070 与集群 5090 都是 `sm_120`（Blackwell 消费级，较新，官方 wheel 支持面窄），
而 lovelace 的 A30 是 `sm_80`（Ampere，成熟）。**如果两边用不同的 PyTorch/CUDA/vLLM 版本，
跨架构差异里就混进了软件栈差异** —— E1/E2 的结论会被污染，而且很可能到写结论时才发现。

**决策**：锁定**一个**容器镜像 digest，要求它在 `sm_120` 与 `sm_80` 上都能跑通；镜像 digest 进
每一条 run record。若打不通，则**不假装它是同一个栈** —— 把软件栈提升为显式实验轴，
每格标注其版本组合。

**备选**：各平面各装各的原生环境。**否掉原因**：这正是会产生隐藏混杂因子的做法。

**代价**：镜像筛选要花时间；容器内 profiling（Nsight）需要额外权限配置。

## ADR-14：spike 前置，判据在跑之前写死

*决定于 2026-08-24，设计评审中发现。*

**触发事实**：headline "某变量能把唯一输出数从 1 变 k" 是**经验假设，不是已知事实**。
Thinking Machines 的结论来自特定模型与特定 vLLM 版本且是博客；vLLM/SGLang 近一年一直在往
batch-invariance 方向修，装的版本可能已经不复现该现象。

**决策**：在投入平台建设前，先花一天用本地 0.5B 验证现象存在，判据 L0/L1/L2 **在跑之前写死**，
不得事后调整。三种结局都有预案（见 PLAN §4），任何一种都带数据回来重定 headline，不自行改了继续跑。

**备选**：不做 spike，文献已足够。**否掉原因**：整个计划的差异化押在这一个现象上，
验证成本是一天，失败代价是三周白做。

**代价**：推迟一天开始建平台。

## ADR-15：不设日历预算，改"随时可交付"的顺序

*决定于 2026-08-24。*

**备选**：现在定死 2–3 周 / 4–6 周 / 8 周+ 的预算并据此裁剪。

**为什么否掉**：两个最大的不确定性 —— GPU 分区权限、现象是否存在 —— 都还没解，现在定日历预算
等于在猜。

**决策**：把步骤 0–3 定为不可裁剪的核心（本地、无外部依赖），步骤 4 以后各自独立可丢，
每完成一个就是一个完整的对外资产。

**代价**：没有一个可以对外承诺的完成日期。但对求职场景这反而更优 —— 任何时点被问到都有完整的
东西可讲，而不是一个做了一半的矩阵。
