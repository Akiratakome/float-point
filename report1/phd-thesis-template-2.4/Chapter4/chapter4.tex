\chapter{Implementation and Experimental Design}

\section{Implementation Route and Comparability Principle}
\label{sec:implementation-route}
% <<SECTION_1_BEGIN>>
Report 1 uses a stand-alone Euler implementation so that the finite-volume
update stays fixed while precision, backend, and selected build choices are
varied. The real type is selected at configuration time and is then used as the
single scalar type in the solver:

\begin{center}
\begin{tabular}{lll}
\toprule
Configuration choice & Compile-time definition & Report role \\
\midrule
\texttt{-DFLOAT\_PRECISION=float}  & \texttt{HRSC\_REAL=float}  & IEEE binary32 run \\
\texttt{-DFLOAT\_PRECISION=double} & \texttt{HRSC\_REAL=double} & IEEE binary64 run \\
\texttt{-DENABLE\_CUDA=ON}         & \texttt{HRSC\_HAS\_CUDA}   & enables \texttt{device=gpu} \\
\bottomrule
\end{tabular}
\end{center}

This design keeps the precision comparison to two storage formats,
binary32 and binary64~\citep{ieee754_2019}. Higher-precision extensions, such
as a Boost::Multiprecision route, are outside the Report 1 evidence scope.
When CUDA is enabled, the same executable interface serves CPU and CUDA
backends; \texttt{device=cpu/gpu} selects the backend at runtime.

The toolchain boundary is part of the experimental design: Toro3 and Toro5 use
Windows BuildTools; Sod, Liska-Wendroff configuration 3 (LW3), and
Liska-Wendroff configuration 12 (LW12) use Linux/WSL; each CPU/GPU
comparison stays within one matched binary/configuration.

The four implementation features that make this comparison auditable are:
\begin{enumerate}
  \item fp32/fp64 source-level templating via \texttt{HRSC\_REAL}, so the same
        source compiles to either precision;
  \item CMake \texttt{ENABLE\_CUDA} build switch plus runtime
        \texttt{device=cpu/gpu} selection, producing matched within-binary
        CPU/GPU comparisons;
  \item a Python regression harness that re-runs the validation matrix and
        checks outputs against stored references;
  \item the matched-binary CPU--GPU switch, so bit-identity claims are not
        confused with toolchain or compiler-flag differences.
\end{enumerate}
% <<SECTION_1_END>>

\section{Algorithmic Structure of the Implementation}
% <<SECTION_2_BEGIN>>
At run time the executable reads the configuration, selects the initial
condition, boundary modes, flux solver, and device, then dispatches to the CPU
solver or to CUDA. CUDA is the NVIDIA GPU programming model used here and is
available only in binaries built with \texttt{ENABLE\_CUDA}. Each step fills
ghost cells, chooses a CFL-limited time step, applies directional sweeps, and
updates time. The sweep uses MUSCL--Hancock reconstruction with HLLC or
Rusanov fluxes~\citep{toro2009}.

The conservative state stores the variable index as the fastest-varying
dimension and uses $n_g$ ghost-cell layers on every side, giving CPU loops and
GPU kernels the same logical cell ordering and boundary rules. The CFL scan
computes
\begin{equation}\label{eq:ch4-cfl-scan}
  \Delta t = C_{\mathrm{CFL}}
  \min\left(\frac{\Delta x}{\max_{i,j}(|u|+c)},
             \frac{\Delta y}{\max_{i,j}(|v|+c)}\right),
\end{equation}
then clips the result to the requested final time. Equation~\ref{eq:ch4-cfl-scan}
is a deterministic max/min comparison over wave-speed candidates, not a
summation reduction, so it is not evidence for summation-order sensitivity.
Algorithm~\ref{alg:step-dispatch} summarises the dispatch, and
Algorithm~\ref{alg:muscl-hancock} expands the per-cell predictor.

Reproducibility follows the harness sequence: configuration, build, run,
measurement, aggregation, and plotting. Matrix runs copy the source
configuration into a generated run directory rather than editing it in place,
then save stdout, stderr, binary path, precision, device, build label, command,
and output path as metadata. Chapter~5 uses the aggregated summaries and
report-facing figures from these runs, not raw grids as direct evidence.

\begin{algorithm}
\caption{Report-Level Solver Dispatch}\label{alg:step-dispatch}
\begin{algorithmic}[1]
\State Read configuration
\State Select CPU or CUDA
\State Fill ghost cells and compute clipped $\Delta t$
\State Apply one 1D sweep, or alternate $x/y$ sweep order in 2D
\State Refill ghost cells between 2D sweeps
\State Advance time with Kahan summation~\citep{higham_2002}
\State Write configured outputs
\end{algorithmic}
\end{algorithm}

\begin{algorithm}
\caption{MUSCL--Hancock face-state construction for one cell, one direction}
\label{alg:muscl-hancock}
\begin{algorithmic}[1]
\Function{ReconstructFaces}{$\bar U_{i-1}^{n}, \bar U_i^{n}, \bar U_{i+1}^{n}, \Delta x, \Delta t$}
  \State $\delta^{-} \gets \bar U_i^{n} - \bar U_{i-1}^{n}$
  \State $\delta^{+} \gets \bar U_{i+1}^{n} - \bar U_i^{n}$
  \State $\sigma_i \gets \textsc{Minmod}(\delta^{-}, \delta^{+})$ \Comment{Eq.~\eqref{eq:ch3-minmod-def}}
  \State $U_{i,L}^{n} \gets \bar U_i^{n} - \tfrac{1}{2}\sigma_i$
  \State $U_{i,R}^{n} \gets \bar U_i^{n} + \tfrac{1}{2}\sigma_i$
  \State $\Delta F \gets F(U_{i,R}^{n}) - F(U_{i,L}^{n})$
  \State $\bar U_{i,L}^{n+1/2} \gets U_{i,L}^{n} - \tfrac{\Delta t}{2\Delta x}\,\Delta F$
  \State $\bar U_{i,R}^{n+1/2} \gets U_{i,R}^{n} - \tfrac{\Delta t}{2\Delta x}\,\Delta F$
  \State \Return $(\bar U_{i,L}^{n+1/2},\, \bar U_{i,R}^{n+1/2})$
\EndFunction
\end{algorithmic}
\end{algorithm}

The CUDA path uses separate kernels for boundary handling, face-state
construction, flux evaluation, and conservative updates. Its reconstruction and
update kernels use thread blocks: GPU thread tiles assigned to neighbouring
grid cells. The main two-dimensional kernels use $16\times16$ tiles, consistent
with \citet{bard_dorelli_2014}. The HLLC branch-rule sensitivity axis is shared
across CPU and CUDA. In the CUDA CFL stage, ordered comparisons make the
selected $\Delta t$ independent of block-completion order.

{\sloppy
CPU sweep loops use OpenMP static schedules, giving fixed loop-iteration
assignment to CPU threads. The CPU CFL scan uses \texttt{reduction(max:\dots)}
over wave-speed candidates, a deterministic comparison rather than a
floating-point sum. Verificarlo MCA runs force serial execution because the
\texttt{libinterflop} PRNG is not thread-safe. MPI is not used, so comparisons
exclude inter-process ordering.\par}

Algorithm~\ref{alg:hllc-flux-select} expands the HLLC interface flux; the
strict-inequality variant tested in Section~\ref{sec:precision-sensitive-decisions}
flips each branch comparator.
\begin{algorithm}
\caption{HLLC interface flux selection (one face)}
\label{alg:hllc-flux-select}
\begin{algorithmic}[1]
\Function{HllcFlux}{$U_L, U_R$}
  \State Compute $(\rho_L,u_L,p_L,a_L)$ from $U_L$; same for $R$
  \State $S_L \gets \min(u_L-a_L,\,u_R-a_R)$ \Comment{Eq.~\eqref{eq:ch3-hllc-wavespeeds}}
  \State $S_R \gets \max(u_L+a_L,\,u_R+a_R)$
  \State $S_\ast \gets \textsc{ComputeContactSpeed}(U_L, U_R, S_L, S_R)$ \Comment{Eq.~\eqref{eq:ch3-hllc-sstar}}
  \If{$S_L \ge 0$} \State \Return $F(U_L)$
  \ElsIf{$S_\ast \ge 0$} \State \Return $F(U_L) + S_L\,(U_{\ast L} - U_L)$
  \ElsIf{$S_R \ge 0$} \State \Return $F(U_R) + S_R\,(U_{\ast R} - U_R)$
  \Else \State \Return $F(U_R)$
  \EndIf
\EndFunction
\end{algorithmic}
\end{algorithm}
% <<SECTION_2_END>>

\section{Precision and Hardware Variants}
% <<SECTION_3_BEGIN>>
The experiment matrix separates precision, hardware, compiler, and branch-rule
effects. The fp32/fp64 axis is a build axis:
\texttt{FLOAT\_PRECISION=float} and \texttt{FLOAT\_PRECISION=double} compile
the same source with different \texttt{HRSC\_REAL} definitions. A matched
device comparison means the same case, executable, precision, and
configuration, changing only \texttt{device=cpu} to \texttt{device=gpu} at run
time inside a CUDA-enabled binary. CPU/GPU statements are therefore
within-case and within-binary claims, not cross-toolchain equivalence claims.

\begin{table}[htbp]
\centering
\small
\begin{tabularx}{\textwidth}{@{}ll>{\raggedright\arraybackslash}X@{}}
\toprule
Scope & Flag & Meaning for the comparison \\
\midrule
CPU & \texttt{-ffp-contract=off} & forbids compiler contraction of
\(a\times b+c\) into a fused multiply-add (FMA), avoiding a different
single-rounding path \\
CPU & \texttt{-fno-fast-math} & disables the fast-math umbrella, including
transformations that may reassociate expressions or weaken IEEE-style
semantics \\
CUDA & \texttt{--fmad=false} & forbids implicit CUDA FMA contraction where the

\bottomrule
\end{tabularx}
\caption{Strict floating-point controls used for matched CPU/GPU comparisons

\label{tab:ch4-strict-flags}
\end{table}

Compiler optimisation and the HLLC wave-speed branch rule are separate axes
from the strict device comparison in Table~\ref{tab:ch4-strict-flags}. The
table is included to define the build controls used when the saved CPU and GPU
states are compared; Chapter~5 reports the measured differences.

Verificarlo runs are diagnostic experiments, not real fp32/fp64 runs. Following
Parker's Monte Carlo arithmetic formulation~\citep{parker_1997} and Denis et
al.'s Verificarlo tool~\citep{denis_etal_2016}, the solver is built through the
MCA/virtual-precision toolchain and sampled with independent seeds. Labels
\texttt{p8}, \texttt{p16}, \texttt{p32}, and \texttt{p53} denote virtual
mantissa settings applied by the tool, not binary storage formats; in
particular, \texttt{p32} is not IEEE binary32/fp32. For a primitive component
\(q_j\), the sample standard deviation
\(\sigma_{\mathrm{FP},j}=\operatorname{std}_k(q_j^{(k)})\) defines a local
roundoff scale that can be compared with the field magnitude or with the local
reference error. Direct statements about fp32 adequacy come only from real
fp32/fp64 comparisons against the chosen reference solution.

\section{Test-Case Matrix and Metrics}
% <<SECTION_4_BEGIN>>
The validation set exercises one- and two-dimensional Euler problems under the
same implementation axes. Sod provides the lower-severity exact-reference
baseline~\citep{sod_1978}. Toro's tests supply the one-dimensional strong
waves, and Liska and Wendroff's benchmark set supplies the two-dimensional
quadrant Riemann problems~\citep{toro2009,
liska_wendroff_2003}. The supersonic-wave requirement is met by four entries
in this matrix: Toro3 has a right-running supersonic shock, Toro5 has
colliding supersonic shocks, and LW3 and LW12 contain supersonic
quadrant-interface shocks in Liska and Wendroff's initial states. Sod is
retained as the lower-severity exact-reference baseline rather than as the main
supersonic example. Table~\ref{tab:ch4-design-matrix} records this design
coverage; Chapter~5 reports the measured values.

The scalar comparisons use field norms on the saved state: \(L_1\),
\(L_\infty\), and \(\mathrm{ULP}_{\max}\). For two-dimensional density images,
SSIM measures image-structure similarity; values near 1 indicate closer
agreement with the reference image. Precision adequacy uses the
reference-scaled ratio
\begin{equation}\label{eq:ch4-rref}
R_{\mathrm{ref}} =
\frac{\|U_{\mathrm{fp32}}-U_{\mathrm{fp64}}\|_1}
     {\|U_{\mathrm{fp64}}-U_{\mathrm{ref}}\|_1}.
\end{equation}
A value below 1 means that the fp32--fp64 gap is below the chosen
reference/discretisation scale; values near or above 1 mean that it is
comparable to, or larger than, that scale. If the denominator is zero, the
comparison is degenerate and is not interpreted as a finite adequacy ratio.
CPU/GPU entries are matched-binary comparisons under the device-selection rule
of Section~\ref{sec:implementation-route}.

\section{Reference-Solution Strategy}
% <<SECTION_5_BEGIN>>
The reference solution is part of the experimental design, because a
float--double or CPU--GPU difference is only meaningful once it has a scale.
For Sod and the Toro shock tubes used in the validation tables, the comparison
is made against analytic exact Riemann references, so the reported error mixes
discretisation and floating-point effects in a controlled one-dimensional
setting described by \citet{toro2009}. For the two-dimensional
Liska--Wendroff problems, no exact reference is used. LW3 is compared with a
\(1600^2\) fp64 numerical reference, and Liska--Wendroff configuration 12
(LW12) is compared with an \(800^2\) fp64 numerical reference in the benchmark
family of \citet{liska_wendroff_2003}.

The lower-grid two-dimensional comparisons map these high-resolution
references to the candidate grid before metrics are computed. The conserved
variables in the reference grid are averaged over integer-ratio cell blocks,
then the candidate and block-averaged reference states are converted to
primitive variables for the reported norms and SSIM. Thus LW3 maps
\(1600^2\) to \(400^2\) or \(200^2\) by \(4\times4\) or \(8\times8\) block
averaging, while LW12 maps \(800^2\) to \(400^2\) or \(200^2\) by \(2\times2\)
or \(4\times4\) block averaging. This is a conservative mapping step, not an
exact-solution construction.

Ratios such as
\(\|U_{\mathrm{fp32}}-U_{\mathrm{fp64}}\|_1/
\|U_{\mathrm{fp64}}-U_{\mathrm{ref}}\|_1\) bound precision drift relative to
the reference scale, not absolute terms~\citep{higham_2002}. CPU/GPU entries
are matched same-precision final-state comparisons; checkpointed summaries
bound only saved-output behaviour, not stage-by-stage identity.
% <<SECTION_5_END>>
