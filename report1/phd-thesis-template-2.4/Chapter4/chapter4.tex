\chapter{Implementation and Experimental Design}

\section{Implementation Route and Comparability Principle}
\label{sec:implementation-route}
% <<SECTION_1_BEGIN>>
Report~1 uses a stand-alone CPU/CUDA Euler implementation. The brief permits this, and source-level control of the precision-sensitive decision points enumerated in Section~\ref{sec:precision-sensitive-decisions} (FMA contraction, HLLC branch rule, fast-math reassociation) is easier than through a framework's flux abstraction. The real type is selected at configuration time and is then used as the single scalar type in the solver:

\begin{center}
\begin{tabular}{lll}
\toprule
Configuration choice & Compile-time definition & Report role \\
\midrule
\texttt{-DFLOAT\_PRECISION=float}  & \texttt{HRSC\_REAL=float}  & IEEE binary32 run \\
\texttt{-DFLOAT\_PRECISION=double} & \texttt{HRSC\_REAL=double} & IEEE binary64 run \\
\texttt{-DENABLE\_CUDA=ON}         & \texttt{HRSC\_HAS\_CUDA}   & enables \texttt{device=gpu} \\
\bottomrule
\end{tabular}
\end{center}

This design keeps the precision comparison to two storage formats,
binary32 and binary64~\citep{ieee754_2019}. Higher-precision extensions, such
as a Boost::Multiprecision route, are outside the Report 1 evidence scope.
When CUDA is enabled, the same executable interface serves CPU and CUDA
backends; \texttt{device=cpu/gpu} selects the backend at runtime.

The toolchain boundary is part of the experimental design: Toro3 and Toro5 use
Windows BuildTools; Sod, Liska-Wendroff configuration 3 (LW3), and
Liska-Wendroff configuration 12 (LW12) use Linux/WSL; each CPU/GPU
comparison stays within one matched binary/configuration.

Four design features make the comparison auditable: source-level \texttt{HRSC\_REAL} templating, the \texttt{ENABLE\_CUDA} build switch with runtime \texttt{device=cpu/gpu} selection, a Python regression harness, and matched-binary CPU/GPU outputs.
% <<SECTION_1_END>>

\section{Algorithmic Structure of the Implementation}
% <<SECTION_2_BEGIN>>
The executable reads the configuration, selects initial condition, boundary
modes, flux solver, and device, then dispatches to the CPU solver or to CUDA,
available only in binaries built with \texttt{ENABLE\_CUDA}. Each step
fills ghost cells, chooses a CFL-limited time step, applies directional
MUSCL--Hancock sweeps with HLLC or Rusanov fluxes~\citep{toro2009}, and updates
time.

The conservative array is cell-major:
\texttt{((j+ng)*nx\_total + (i+ng))*NVars + var}, with the four Euler variables
contiguous per cell. This array-of-structures-like layout gives CPU loops and
GPU kernels the same indexing and boundary rules; it is for comparability, not
a throughput-optimal GPU alternative to a structure-of-arrays design. The CFL
scan computes
\begin{equation}\label{eq:ch4-cfl-scan}
  \Delta t = C_{\mathrm{CFL}}
  \min\left(\frac{\Delta x}{\max_{i,j}(|u|+c)},
             \frac{\Delta y}{\max_{i,j}(|v|+c)}\right),
\end{equation}
then clips the result to the requested final time. Equation~\ref{eq:ch4-cfl-scan}
is an ordered max/min reduction, not an unordered floating-point summation, so
the selected \(\Delta t\) does not depend on reduction order. The
conserved-state write path emits raw binary conservative-state grids and
contains no floating-point summation reduction; CPU/GPU comparisons read these
saved binary grids and the metrics \(L_1\), \(L_\infty\),
\(\mathrm{ULP}_{\max}\) are computed from them, not from rounded text output.
The simulation clock uses the compensated-summation update of Chapter~2; this
applies only to the scalar time counter. Algorithms~\ref{alg:step-dispatch}
and~\ref{alg:muscl-hancock} summarise dispatch and the per-cell predictor.
Reproducibility follows the harness sequence: configure, build, run, measure,
aggregate, and plot. Matrix runs copy the source configuration into a
generated run directory, save stdout, stderr, binary path, precision, device,
build label, command, and output path, and supply Chapter~5 with aggregated
summaries and report-facing figures rather than raw grids.

\begin{algorithm}
\caption{Time-stepping loop with dimensional splitting and Kahan-compensated time accumulation}
\label{alg:step-dispatch}
\begin{algorithmic}[1]
\Function{AdvanceToFinalTime}{$U^{0}, t_{\mathrm{end}}, C_{\mathrm{CFL}}$}
  \State $U \gets U^{0}$;\quad $t \gets 0$;\quad $n_{\mathrm{step}} \gets 0$;\quad $c \gets 0$ \Comment{$c$: Kahan compensation}
  \While{$t < t_{\mathrm{end}}$}
    \State \textsc{RefillGhostCells}($U$)
    \State $\Delta t \gets C_{\mathrm{CFL}}\,\min\!\left(\Delta x/\max_{i,j}(|u|+c_s),\;\Delta y/\max_{i,j}(|v|+c_s)\right)$ \Comment{Eq.~\eqref{eq:ch4-cfl-scan}}
    \State $\Delta t \gets \min(\Delta t,\; t_{\mathrm{end}} - t)$ \Comment{clip to final time}
    \If{2D \textbf{and} $n_{\mathrm{step}}$ is even}
      \State $U \gets \textsc{XSweep}(U, \Delta t)$;\quad \textsc{RefillGhostCells}($U$);\quad $U \gets \textsc{YSweep}(U, \Delta t)$
    \ElsIf{2D}
      \State $U \gets \textsc{YSweep}(U, \Delta t)$;\quad \textsc{RefillGhostCells}($U$);\quad $U \gets \textsc{XSweep}(U, \Delta t)$
    \Else
      \State $U \gets \textsc{XSweep}(U, \Delta t)$ \Comment{1D}
    \EndIf
    \State $(t, c) \gets \textsc{KahanAdd}(t, \Delta t, c)$ \Comment{compensated summation~\citep{higham_2002}}
    \State $n_{\mathrm{step}} \gets n_{\mathrm{step}} + 1$
  \EndWhile
  \State \Return $U$
\EndFunction
\end{algorithmic}
\end{algorithm}

\begin{algorithm}
\caption{MUSCL--Hancock face-state construction for one cell, one direction}
\label{alg:muscl-hancock}
\begin{algorithmic}[1]
\Function{ReconstructFaces}{$\bar U_{i-1}^{n}, \bar U_i^{n}, \bar U_{i+1}^{n}, \Delta x, \Delta t$}
  \State $\delta^{-} \gets \bar U_i^{n} - \bar U_{i-1}^{n}$
  \State $\delta^{+} \gets \bar U_{i+1}^{n} - \bar U_i^{n}$
  \State $\sigma_i \gets \textsc{Minmod}(\delta^{-}, \delta^{+})$ \Comment{Eq.~\eqref{eq:ch3-minmod-def}}
  \State $U_{i,L}^{n} \gets \bar U_i^{n} - \tfrac{1}{2}\sigma_i$
  \State $U_{i,R}^{n} \gets \bar U_i^{n} + \tfrac{1}{2}\sigma_i$
  \State $\Delta F \gets F(U_{i,R}^{n}) - F(U_{i,L}^{n})$
  \State $\bar U_{i,L}^{n+1/2} \gets U_{i,L}^{n} - \tfrac{\Delta t}{2\Delta x}\,\Delta F$
  \State $\bar U_{i,R}^{n+1/2} \gets U_{i,R}^{n} - \tfrac{\Delta t}{2\Delta x}\,\Delta F$
  \State \Return $(\bar U_{i,L}^{n+1/2},\, \bar U_{i,R}^{n+1/2})$
\EndFunction
\end{algorithmic}
\end{algorithm}

The CUDA path decomposes the update into separate kernels for boundary handling, face-state construction, flux evaluation, conservative update, and a block-wise reduction for the CFL stage. The HLLC flux kernel (Algorithm~\ref{alg:hllc-flux-select}) is the principal warp-divergence site: in mixed-wave regions, threads within a warp can resolve to different branches of the wave-pattern test ($S_L \ge 0$ vs.\ $S_\ast \ge 0$ vs.\ $S_R \ge 0$), and the warp serialises the divergent paths rather than executing them in lock-step. CPU and CUDA therefore share the same HLLC branch-rule sensitivity axis: near mixed-wave cells, branch choices can diverge within a warp even when no aggregate CPU--GPU saved-state divergence is observed. The cell-major layout introduced earlier in this section is a CPU/GPU comparability choice---identical indexing on both sides---rather than a throughput-optimal structure-of-arrays design, so it constrains coalescing and bounds GPU throughput. Shared memory is used only for the CFL block reduction, not as a tiled stencil cache, leaving global-memory bandwidth as the dominant traffic for reconstruction, flux, and update. This is consistent with Table~\ref{tab:ch4-runtime-minimatrix}: the fp64 LW3 row, where GPU wall-clock sits close to CPU, matches memory-bound behaviour saturating fp64 bandwidth, while the fp32 LW3 row, where GPU is faster than CPU, is consistent with fp32 halving per-element traffic and freeing bandwidth headroom. In the CUDA CFL stage, ordered comparisons make the selected $\Delta t$ independent of block order.

{\sloppy
CPU sweep loops use OpenMP static schedules, giving fixed thread assignments.
The CPU CFL scan uses \texttt{reduction(max:\dots)} over wave-speed candidates,
a deterministic comparison, not a floating-point sum. Verificarlo MCA runs are
serial because the \texttt{libinterflop} PRNG is not thread-safe. MPI is not
used, so comparisons exclude inter-process ordering.\par}

Algorithm~\ref{alg:hllc-flux-select} expands the HLLC interface flux; the
strict-inequality variant tested in Section~\ref{sec:precision-sensitive-decisions}
flips each branch comparator.
\begin{algorithm}
\caption{HLLC interface flux selection (one face)}
\label{alg:hllc-flux-select}
\begin{algorithmic}[1]
\Function{HllcFlux}{$U_L, U_R$}
  \State Compute $(\rho_L,u_L,p_L,a_L)$ from $U_L$; same for $R$
  \State $S_L \gets \min(u_L-a_L,\,u_R-a_R)$ \Comment{Eq.~\eqref{eq:ch3-hllc-wavespeeds}}
  \State $S_R \gets \max(u_L+a_L,\,u_R+a_R)$
  \State $S_\ast \gets \textsc{ComputeContactSpeed}(U_L, U_R, S_L, S_R)$ \Comment{Eq.~\eqref{eq:ch3-hllc-sstar}}
  \If{$S_L \ge 0$} \State \Return $F(U_L)$
  \ElsIf{$S_\ast \ge 0$} \State \Return $F(U_L) + S_L\,(U_{\ast L} - U_L)$
  \ElsIf{$S_R \ge 0$} \State \Return $F(U_R) + S_R\,(U_{\ast R} - U_R)$
  \Else \State \Return $F(U_R)$
  \EndIf
\EndFunction
\end{algorithmic}
\end{algorithm}

\section{Precision and Hardware Variants}
% <<SECTION_3_BEGIN>>
The experiment matrix separates precision, hardware, compiler, and branch-rule
effects. The fp32/fp64 axis sets \texttt{HRSC\_REAL} through the
\texttt{FLOAT\_PRECISION} build option. A matched device comparison keeps the case,
executable, precision, and configuration fixed, changing only
\texttt{device=cpu} to \texttt{device=gpu} inside a CUDA-enabled binary.
CPU/GPU statements are therefore within-case and within-binary, not
cross-toolchain, claims.

Compiler optimisation and the HLLC wave-speed branch rule are separate from the
strict device comparison in Table~\ref{tab:ch4-strict-flags}, which defines the
build controls for the saved CPU/GPU state comparisons reported in Chapter~5.

Verificarlo runs are diagnostic, not real fp32/fp64 runs. Following Parker's
Monte Carlo arithmetic formulation~\citep{parker_1997} and Denis et al.'s
Verificarlo tool~\citep{denis_etal_2016}, the solver is built through the
MCA/virtual-precision toolchain in MCA mode with the random-rounding (RR)
operator, and sampled with independent seeds. The virtual-precision labels
\texttt{p8}, \texttt{p16}, \texttt{p32}, and \texttt{p53} are not IEEE
binary storage formats (see Section~2.4). By design the per-configuration
sample budget is small, so Chapter~5 reads these as a rounding-sensitivity
probe rather than a converged distribution.
For a primitive component \(q_j\), the sample standard deviation
\(\sigma_{\mathrm{FP},j}=\operatorname{std}_k(q_j^{(k)})\) gives a local
roundoff scale for comparison with field magnitude or local reference error.
Verificarlo was chosen because MCA and virtual precision support the reported
p8/p16/p32/p53 rounding-sensitivity diagnostics. RAPTOR remains a possible
future tool for automated mixed-precision source transformation; Report 1 does
not present per-routine precision rewrites. Direct fp32 claims come only from
real fp32/fp64 comparisons against the chosen reference solution.

\section{Test-Case Matrix and Metrics}
% <<SECTION_4_BEGIN>>
The validation set exercises one- and two-dimensional Euler problems under the
same implementation axes. Sod provides the lower-severity exact-reference
baseline~\citep{sod_1978}. Toro's tests supply the one-dimensional strong
waves, and Liska and Wendroff's benchmark set supplies the two-dimensional
quadrant Riemann problems~\citep{toro2009,
liska_wendroff_2003}. The supersonic-wave requirement is met by four entries
in this matrix: Toro3 has a right-running supersonic shock, Toro5 has
colliding supersonic shocks, and LW3 and LW12 contain supersonic
quadrant-interface shocks in Liska and Wendroff's initial states. Sod is
retained as the lower-severity exact-reference baseline rather than as the main
supersonic example. Table~\ref{tab:ch4-design-matrix} records this design
coverage; Chapter~5 reports the measured values.

The scalar comparisons use field norms on the saved state: \(L_1\),
\(L_\infty\), and \(\mathrm{ULP}_{\max}\). For two-dimensional density images,
SSIM measures image-structure similarity; values near 1 indicate closer
agreement with the reference image. Precision adequacy uses the
reference-scaled ratio
\begin{equation}\label{eq:ch4-rref}
R_{\mathrm{ref}} =
\frac{\|U_{\mathrm{fp32}}-U_{\mathrm{fp64}}\|_1}
     {\|U_{\mathrm{fp64}}-U_{\mathrm{ref}}\|_1}.
\end{equation}
A value below 1 means that the fp32--fp64 gap is below the chosen
reference/discretisation scale; values near or above 1 mean that it is
comparable to, or larger than, that scale. If the denominator is zero, the
comparison is degenerate and is not interpreted as a finite adequacy ratio.
CPU/GPU entries are matched-binary comparisons under the device-selection rule
of Section~\ref{sec:implementation-route}.

\section{Reference-Solution Strategy}
% <<SECTION_5_BEGIN>>
The reference solution is part of the experimental design, because a
float--double or CPU--GPU difference is only meaningful once it has a scale.
For Sod and the Toro shock tubes used in the validation tables, the comparison
is made against analytic exact Riemann references, so the reported error mixes
discretisation and floating-point effects in a controlled one-dimensional
setting described by \citet{toro2009}. For the two-dimensional
Liska--Wendroff problems, no exact reference is used. LW3 is compared with a
\(1600^2\) fp64 numerical reference, and Liska--Wendroff configuration 12
(LW12) is compared with an \(800^2\) fp64 numerical reference in the benchmark
family of \citet{liska_wendroff_2003}.
The reference self-convergence summary checks LW3 \(400^2\)-against-\(800^2\)
and \(800^2\)-against-\(1600^2\), supporting the \(1600^2\) field as a
higher-resolution numerical reference; no analogous \(1600^2\) row is claimed
for LW12.

The lower-grid two-dimensional comparisons map these high-resolution
references to the candidate grid before metrics are computed. The conserved
variables in the reference grid are averaged over integer-ratio cell blocks,
then the candidate and block-averaged reference states are converted to
primitive variables for the reported norms and SSIM. Thus LW3 maps
\(1600^2\) to \(400^2\) or \(200^2\) by \(4\times4\) or \(8\times8\) block
averaging, while LW12 maps \(800^2\) to \(400^2\) or \(200^2\) by \(2\times2\)
or \(4\times4\) block averaging. This is a conservative mapping step, not an
exact-solution construction.

Ratios such as
\(\|U_{\mathrm{fp32}}-U_{\mathrm{fp64}}\|_1/
\|U_{\mathrm{fp64}}-U_{\mathrm{ref}}\|_1\) bound precision drift relative to
the reference scale, not absolute terms~\citep{higham_2002}. CPU/GPU entries
are matched same-precision final-state comparisons; checkpointed summaries
bound only saved-output behaviour, not stage-by-stage identity.
% <<SECTION_5_END>>

\section{Regression and Reproducibility Harness}
\label{sec:ch4-regression-harness}
% <<SECTION_6_BEGIN>>
A Python regression harness drives the validation matrix and turns each
configuration into an auditable record. The brief asks for an explicit
description of what testing framework will be used to ensure reproducibility
and how compiler-flag and floating-point tolerance ranges will be explored;
this section gives that description.

\paragraph{Layout.} Three directories partition the work. The C++ entry point
under \texttt{src/} is built by CMake; \texttt{scripts/regression/} carries
the case-level drivers (\texttt{verify\_sod.py}, \texttt{verify\_toro.py},
\texttt{report1\_1d\_feature\_validation.py},
\texttt{run\_comparison.py}, \texttt{convergence.py}); and \texttt{tests/py/}
holds \texttt{pytest} units that re-run those drivers on stored references
and decide pass/fail.

\paragraph{What is checked.} For one-dimensional cases, the harness reads
\texttt{grid.bin} for the candidate run and the analytic exact Riemann
solution at the same final time and grid, computes density, momentum, and
energy \(L_1\), \(L_\infty\), and \(\mathrm{ULP}_{\max}\), and asserts that
each metric is below a per-case tolerance recorded in the test source.
\texttt{test\_report1\_1d\_feature\_validation.py} additionally checks the
feature-band split reported in Table~\ref{tab:ch5-1d-feature-validation}.
For two-dimensional cases, \texttt{run\_comparison.py} block-averages the
high-resolution fp64 reference to the candidate grid and reports
\(L_1\), \(L_\infty\), \(\mathrm{ULP}_{\max}\), and SSIM; the matched
CPU/GPU pairs are byte-compared on \texttt{grid.bin} as well. Verificarlo
runs go through a separate \texttt{precexp} pipeline whose unit tests
(\texttt{test\_precexp\_*.py}) check manifest, configuration, and aggregation
stages independently.

\paragraph{How the axes are swept.} The compiler-flag, branch-rule,
device, and precision axes are not hand-driven; each combination is a row
in a configuration sweep loaded by \texttt{run\_comparison.py} or by the
\texttt{precexp} driver. Each row records build label, compiler version,
flags, precision, device, command line, \texttt{stdout}/\texttt{stderr}
paths, and binary hash before the metrics are written, so a failed
comparison can be rerun from its captured invocation. Per-case tolerances
sit in the test source rather than in a global threshold file, so a
tolerance change is a code change with version-controlled provenance.

\paragraph{What pass/fail means.} A regression failure is one of three
things: a metric assert above its stored tolerance, a missing artifact (no
\texttt{grid.bin}, no exact-reference table), or a configuration mismatch
(precision, device, or solver differing from the manifest). The matched
CPU/GPU zero-drift table in Chapter~5 is therefore not a one-off
measurement; it is the saved output of the harness re-run, and a future
re-run that introduced a non-zero entry would fail
\texttt{test\_float\_regression\_report\_device\_mode.py} on byte
comparison.
% <<SECTION_6_END>>
