\chapter{Implementation and Experimental Design}

\section{Implementation Route and Comparability Principle}
\label{sec:implementation-route}
% <<SECTION_1_BEGIN>>
The Report 1 evidence uses the stand-alone Euler code path rather than an
AMReX application. The AMReX framework of \citet{zhang_etal_2019} remains
relevant to the wider project as a route to adaptive mesh refinement and
accelerator support, but
the reported Euler comparisons do not use AMR or AMReX. The stand-alone route
keeps the comparison narrow: precision, backend, and selected implementation
choices can change while the finite-volume update remains fixed.

Five implementation features support that comparison:
\begin{itemize}\setlength{\itemsep}{0pt}
  \item \textbf{fp32/fp64 templating.} A single \texttt{HRSC\_REAL} alias
        selected by \texttt{FLOAT\_PRECISION} compiles the same source as a
        single- or double-precision binary~\citep{ieee754_2019}.
  \item \textbf{Compile-once device dispatch.} \texttt{ENABLE\_CUDA=ON} builds
        one binary that selects \texttt{device=cpu/gpu} at runtime.
  \item \textbf{Strict-IEEE build mode.} \texttt{STRICT\_IEEE=ON} controls FMA,
        denormal, division, and square-root behaviour on CPU and CUDA.
  \item \textbf{Compile-time variation switches.}
        \texttt{RIEMANN\_STRICT\_INEQUALITY} toggles the HLLC wave-speed
        \texttt{<} versus \texttt{<=} branch; the solver switch selects HLLC
        or Rusanov.
  \item \textbf{Python regression and report harness.} Build provenance, run
        configuration, norms, and ratios are logged for each run.
\end{itemize}
Device evidence uses a disclosed toolchain split: Toro3 and Toro5 are run
through Windows BuildTools, while Sod, LW3, and LW12 use the Linux/WSL
toolchain. Each CPU/GPU comparison is still within-case and matched-binary.
% <<SECTION_1_END>>

\section{Algorithmic Structure of the Implementation}
% <<SECTION_2_BEGIN>>
At run time the executable reads the configuration, selects the initial
condition, boundary modes, flux solver, output format, and device, then
dispatches to the CPU solver or to CUDA when \texttt{ENABLE\_CUDA} is
available. A solver step fills ghost cells, computes a CFL-limited
$\Delta t$, performs one or two directional sweeps, and advances the time
accumulator. The method inside each sweep is MUSCL--Hancock with a
component-wise minbee limiter and HLLC or Rusanov fluxes; HLLC is the main
Report 1 solver because the validation and variation axes require a
Riemann-solver-based scheme of the kind described by \citet{toro2009}.

The conservative state is stored row-major with the variable index as the
fastest-varying dimension and with $n_g$ ghost-cell layers on every side, so
CPU and CUDA kernels use the same indexing convention and boundary-condition
rules.  The CPU CFL scan computes
\[
  \Delta t = C_{\mathrm{CFL}}
  \min\left(\frac{\Delta x}{\max_{i,j}(|u|+c)},
             \frac{\Delta y}{\max_{i,j}(|v|+c)}\right),
\]
then clips the result to the requested final time. Metric collection is kept
outside this update path: scripts compare written conservative states or
primitive tables and aggregate $L_1$, $L_2$, $L_\infty$, and ULP diagnostics.
The dispatch is summarised in Algorithm~\ref{alg:step-dispatch}. Both drivers
advance time with Kahan compensated summation, following the treatment in
\citet{higham_2002}.

\begin{algorithm}
\caption{Report-Level Solver Dispatch}\label{alg:step-dispatch}
\begin{algorithmic}[1]
\State Read configuration and select CPU or CUDA backend
\State Fill ghost cells with the configured boundary conditions
\State Compute CFL-limited $\Delta t$ and clip to final time
\If{$n_y=1$}
    \State Apply one MUSCL--Hancock $x$-sweep
\ElsIf{step index is even}
    \State Apply $x$-sweep, refill ghost cells, then apply $y$-sweep
\Else
    \State Apply $y$-sweep, refill ghost cells, then apply $x$-sweep
\EndIf
\State Advance the time accumulator with Kahan summation
\State Write final grid, or CPU checkpoints, outside the sweep
\end{algorithmic}
\end{algorithm}

The CUDA solver follows the same ordering through boundary, face-state, flux,
and conservative-update kernels, with $16\times16$ thread blocks for
reconstruction, matching the GPU MUSCL-Hancock baseline of
\citet{bard_dorelli_2014}. Its HLLC wrappers
call the same \texttt{hllc.hpp} flux algebra as the CPU path, so the
\texttt{<} versus \texttt{<=} branch rule is a shared sensitivity axis. For
the CFL stage, CUDA reduces stable cellwise time-step candidates through
ordered floating-point bits, keeping the selected $\Delta t$ independent of
block-completion order.

{\sloppy
CPU sweep loops use static OpenMP schedules and the CFL scan uses an explicit
\texttt{reduction(max:\dots)} clause. Verificarlo MCA runs force serial
execution because the \texttt{libinterflop} PRNG is not thread-safe. MPI is not
used, so the reported hardware, precision, and compiler comparisons are not
mixed with inter-process ordering or domain-decomposition effects.\par}
% <<SECTION_2_END>>

\section{Precision and Hardware Variants}
% <<SECTION_3_BEGIN>>
The experiment matrix separates precision, hardware, compiler, and branch-rule
effects.  The same input file selects the test name, grid size, final time,
flux solver, boundary conditions, and output format before backend dispatch.
The fp32/fp64 axis is a build axis:
\texttt{FLOAT\_PRECISION=float} and \texttt{FLOAT\_PRECISION=double} compile
the same source with different \texttt{HRSC\_REAL} definitions.  The CPU/GPU
axis is a runtime axis inside CUDA-enabled binaries: a run with
\texttt{device=cpu} and a run with \texttt{device=gpu} use the same configured
executable when \texttt{ENABLE\_CUDA} has been enabled.  Where matched device
evidence is used, \texttt{STRICT\_IEEE=ON} applies strict CPU flags and
corresponding CUDA controls on fused multiply-add, denormals, division, and
square root.  {\sloppy
The recorded flags include \texttt{-ffp-contract=off} and
\texttt{-fno-fast-math} on CPU, and \texttt{--fmad=false},
\texttt{--ftz=false}, \texttt{--prec-div=true}, and
\texttt{--prec-sqrt=true} on CUDA.\par} Compiler optimisation and the HLLC
wave-speed branch rule are separate axes.

CPU/GPU statements are within-case and within-binary, not
cross-toolchain equivalence claims.

Verificarlo runs are diagnostic experiments, not real fp32/fp64 runs.  The
solver is built through the MCA/virtual-precision toolchain and sampled with
independent seeds; labels p8, p16, p32, and p53 denote virtual mantissa
settings applied by the tool, not binary storage formats, following the
Monte Carlo arithmetic formulation of \citet{parker_1997} and the Verificarlo
tool of \citet{denis_etal_2016}.  For a primitive
component $q_j$, the sample standard deviation
$\sigma_{\mathrm{FP},j}=\operatorname{std}_k(q_j^{(k)})$ defines a local
roundoff scale that can be compared with the field magnitude or with the
local reference error, supporting spatial discussion of sensitivity near
smooth regions and wave fronts.  Direct statements about fp32 adequacy come
only from real fp32/fp64 comparisons against the chosen reference solution.
% <<SECTION_3_END>>

\section{Test-Case Matrix and Metrics}
% <<SECTION_4_BEGIN>>
The selected validation cases exercise the same implementation axes on one-
and two-dimensional Euler problems.  \citet{sod_1978} gives the standard
shock-tube baseline with an exact Riemann reference.  Toro3 and Toro5 add a
right-running supersonic shock and a collision of supersonic shocks from the
test set in \citet{toro2009}.  Liska--Wendroff configuration 3 (LW3) and
Liska--Wendroff configuration 12 (LW12) test multidimensional wave interaction,
with supersonic shock segments identified from the benchmark definitions of
\citet{liska_wendroff_2003}. Table~\ref{tab:ch4-design-matrix}
records the intended coverage; Chapter~5 reports the measured values.

The metrics named in the design matrix are field norms ($L_1$, $L_\infty$,
ULP, plus SSIM for two-dimensional images) and reference- or
discretisation-scaled ratios that divide an fp32--fp64 difference by the
corresponding fp64--reference or grid-refinement error; Chapter~5 states the
formal definitions before first use.  CPU/GPU entries are matched-binary
comparisons under the device-selection rule of
Section~\ref{sec:implementation-route}.

\section{Reference-Solution Strategy}
% <<SECTION_5_BEGIN>>
The reference solution is part of the experimental design, because a
float--double or CPU--GPU difference is only meaningful once it has a scale.
For Sod and the Toro shock tubes used in the validation tables, the comparison
is made against analytic exact Riemann references, so the reported error mixes
discretisation and floating-point effects in a controlled one-dimensional
setting described by \citet{toro2009}.  For the two-dimensional Liska--Wendroff problems,
no analytic reference is used.  LW3 is compared with an $N=1600$ fp64
numerical reference, and Liska--Wendroff configuration 12 uses an
\(N=800\) fp64 numerical reference for the reference-scaled fp32--fp64 ratios
in the benchmark family of \citet{liska_wendroff_2003}.  These high-resolution references provide the
discretisation-error scale used in the reference-scaled ratios; if that scale
dominates the numerator, the ratio should be read as a bound on precision drift
relative to the chosen reference, not as an independent estimate of the
rounding error~\citep{higham_2002}.

This strategy is load-bearing for the later interpretation.  Ratios such as
\(\|U_{\mathrm{fp32}}-U_{\mathrm{fp64}}\|_1/
\|U_{\mathrm{fp64}}-U_{\mathrm{ref}}\|_1\) say whether precision drift is
small relative to the chosen reference error, not whether fp32 is generally
adequate.  CPU/GPU rows are instead final-state conservative-state
comparisons between matched same-precision outputs.  Checkpointed CPU/GPU
summaries are used only to bound time-evolution statements at the saved
outputs, not to prove stage-by-stage identity.
% <<SECTION_5_END>>
